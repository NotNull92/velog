<h2 id="🎮-prologue--2편에서-예고한-admin-대시보드-드디어-착수">🎮 Prologue : 2편에서 예고한 Admin 대시보드, 드디어 착수</h2>
<p>2편에서 &quot;다음 편에는 Admin 대시보드 구현과 Vercel 배포로 돌아오겠다. 아마도.&quot; 라고 적었다.</p>
<p>그 &quot;아마도&quot;가 10일이나 걸렸다. WITCHDICE 프로토타이핑 챌린지 때문이었다. 6인 인디팀에서 리드 개발자를 맡아서 StateMachine 아키텍처 설계하고, 절차적 맵 생성 시스템 포팅하고, 멀티씬 비동기 전환 시스템 짜느라 정신이 나갈 뻔했다. 뇌의 Update()가 <code>Time.deltaTime</code>을 0으로 반환하는 수준이었다.</p>
<p>근데 오늘 드디어 마음을 다잡고 포트폴리오로 돌아왔다. 유니티를 잠시 끄고 VS Code를 켰다. 씬 전환 로딩이 길어서 그런지 심장이 좀 떨렸다.</p>
<p><strong>&quot;좋아. 오늘은 Admin 대시보드를 만든다.&quot;</strong></p>

<h2 id="⚔️-scene-1--화면-전환-그게-뭔데요">⚔️ Scene 1 : 화면 전환? 그게 뭔데요?</h2>
<p>Admin 대시보드를 만들려면 일단 화면 전환이 필요했다. 터미널 → 포트폴리오 → 관리자 대시보드. 세 개의 화면을 어떻게 왔다 갔다 하지? <code>Additive</code> 씬 로딩도 아니고 <code>Single</code>도 아닌 그 애매한 느낌.</p>
<pre><code class="language-jsx">// App.jsx
const [isAuthenticated, setIsAuthenticated] = useState(false);
const [isAdmin, setIsAdmin] = useState(false);</code></pre>
<p>상태를 두 개 두면 된다. <code>isAuthenticated</code>가 false면 터미널, true면 포트폴리오. 그리고 <code>isAdmin</code>이 true면 관리자 대시보드.</p>
<p>유니티로 치면 <code>SceneManager.LoadScene(&quot;AdminScene&quot;)</code> 같은 건데, React에서는 상태 하나만 바꾸면 화면이 알아서 갈아끼워진다. <code>AnimatePresence</code> 덕분에 화면 전환 애니메이션도 자동으로 붙는다. <code>SceneManager</code>한테 <code>LoadSceneAsync</code> 걸어놓고 <code>allowSceneActivation</code> 플래그 만지작거리는 그 삽질이 여기선 필요 없다고?</p>
<pre><code class="language-jsx">&lt;AnimatePresence mode=&quot;wait&quot;&gt;
  {!isAuthenticated ? (
    &lt;Terminal key=&quot;terminal&quot; onAuthenticated={handleAuthenticated} /&gt;
  ) : isAdmin ? (
    &lt;AdminDashboard key=&quot;admin&quot; onExit={handleExitAdmin} /&gt;
  ) : (
    &lt;MainPortfolio key=&quot;portfolio&quot; onAdminMode={handleAdminMode} /&gt;
  )}
&lt;/AnimatePresence&gt;</code></pre>
<p>오... 이거 꽤 직관적이다. 유니티에서 씬 전환할 때 <code>DontDestroyOnLoad</code> 걸어놓은 매니저 오브젝트에서 상태 관리하는 것과 비슷한데, 훨씬 간단하다. 싱글톤 패턴으로 GameManager 만들어놓고 <code>Instance == null</code> 체크하다가 눈 돌아가는 그 루틴이 없다니 감격스럽다.</p>
<p><code>onAdminMode</code> prop을 MainPortfolio에 넘겨서, Admin 비밀번호 인증 성공 시 부모(App)에게 &quot;나 이제 관리자 모드야!&quot; 하고 알려주는 구조다.</p>
<p><strong>이벤트 시스템? 아, 그냥 콜백 함수구나.</strong> 유니티에서 <code>Action</code> 이벤트 델리게이트 쓰는 것과 똑같다. <code>UnityAction</code>이니 <code>System.Action&lt;T&gt;</code>이니 제네릭 타입 몇 개 넘길지 고민하다가 <code>UnityEvent</code>로 바꿀까 말까 하는 그 혼돈의 카오스가 여기선 그냥 <code>(callback) =&gt;</code> 끝이다. 이 맛에 웹 하나 보다.</p>

<h2 id="💀-scene-2--css-스크롤-지옥-뇌가-가비지컬렉터한테-런타임에-수거당한-기분">💀 Scene 2 : CSS 스크롤 지옥 (뇌가 가비지컬렉터한테 런타임에 수거당한 기분)</h2>
<p>이건 오늘 진짜 멘탈이 나간 부분이다. <code>MissingReferenceException</code>이 영혼에서 터진 느낌.</p>
<p>포트폴리오 메인 화면에서 탭 내용이 길어지면 스크롤이 안 됐다. 프로젝트 카드가 5개 넘어가면 화면 밖으로 나가버린다. <strong>보이지 않는 프로젝트는 존재하지 않는 것과 같다.</strong> (양자역학의 관측 문제? 아니면 그냥 내 CSS 실력 문제?) <code>Culling</code>이 아니라 진짜로 없어지면 어떡하라고.</p>
<pre><code>&gt; AI야, tab-container에 스크롤이 안 돼. 뭐가 문제야?</code></pre><p>AI가 코드를 뜯어보더니 이렇게 말했다.</p>
<p><strong>&quot;flexbox 체인이 끊어졌습니다.&quot;</strong></p>
<p>...뭐라고? <code>NullReferenceException: Object reference not set to an instance of an object</code> 급의 충격이었다.</p>
<p>문제를 요약하면 이렇다. <code>#root → .app → .portfolio-container → .portfolio-content → .tab-container</code> 이렇게 flexbox가 중첩되어 있는데, <code>.app</code> 클래스에 스타일이 정의되어 있지 않았다. 즉, <code>height: 100%</code>가 안 먹혀서 자식들이 &quot;나 몇 픽셀로 해야 돼?&quot; 하고 서로 쳐다보고 있는 상태였다. 부모 RectTransform의 anchor가 설정 안 돼 있는데 자식한테 Stretch하라는 거랑 뭐가 다르냐.</p>
<pre><code class="language-css">/* .app 클래스가 비어 있었다... */</code></pre>
<p>유니티로 치면 Canvas의 RectTransform 세팅이 안 되어 있어서 자식 UI들이 화면 밖으로 날아가는 것과 같다. 레이아웃 그룹(Layout Group)은 있는데 부모의 크기가 0이면 자식도 0이잖아. 똑같은 문제다. <code>ContentSizeFitter</code>를 달아도 부모가 <code>Preferred Size</code>를 모르면 자식은 그냥 우주 미아다.</p>
<pre><code class="language-css">html, body, #root, .app {
  height: 100%;
  width: 100%;
}

.app {
  display: flex;
  flex-direction: column;
}</code></pre>
<p>이거 한 줄 추가하는 데에 30분이 걸렸다. CSS flexbox, 너는 나의 영원한 숙적이다. 유니티 <code>LayoutGroup</code>의 <code>childForceExpandWidth</code>보다 더 악질적인 존재.</p>
<p>그리고 스크롤바를 보이지 않게 하되 기능은 유지하고 싶었다.</p>
<pre><code class="language-css">::-webkit-scrollbar-thumb {
  background: transparent;
}</code></pre>
<p>투명 스크롤바. 보이지 않지만 존재한다. 유니티의 <code>Scrollbar</code> 컴포넌트를 비활성화하되 <code>ScrollRect</code>는 살려둔 것과 같은 느낌. 소름 돋는 은유가 아니라 진짜로 똑같은 상황이었다. <code>gameObject.SetActive(false)</code> 하면 안 되고 <code>CanvasGroup.alpha = 0</code>으로 해야 하는 그 미묘한 차이.</p>

<h2 id="🔥-scene-3--admin-대시보드-구현-trello를-클론하다">🔥 Scene 3 : Admin 대시보드 구현 (Trello를 클론하다)</h2>

<p>상태가 3개. <code>projects</code>는 프로젝트 목록, <code>showModal</code>은 프로젝트 추가/수정 모달, <code>editingProject</code>는 현재 수정 중인 프로젝트. 유니티의 GameManager에서 여러 서브 매니저 참조하는 것과 비슷한데, React는 그냥 <code>useState</code> 하나씩 선언하면 끝이다. 간단해. <code>[SerializeField] private</code> 붙이고 인스펙터에서 드래그 앤 드롭으로 참조 걸어주는 그 노가다가 없다니. 눈물이 좀 난다.</p>
<h3 id="crud-기능">CRUD 기능</h3>
<p><strong>Create</strong>: <code>[ NEW PROJECT ]</code> 버튼 클릭 → 모달 오픈 → 폼 작성 → 저장</p>
<pre><code class="language-jsx">const handleSaveProject = (projectData) =&gt; {
  if (editingProject) {
    setProjects(projects.map(p =&gt; 
      p.id === editingProject.id ? { ...projectData, id: p.id } : p
    ));
  } else {
    const newProject = { ...projectData, id: Date.now() };
    setProjects([...projects, newProject]);
  }
};</code></pre>
<p><code>Date.now()</code>를 ID로 쓴다. 유니티에서 <code>System.Guid.NewGuid()</code> 쓰는 것과 같은 느낌인데, 훨씬 간단하다. 게다가 애초에 로컬에서만 쓸 거라 중복 걱정도 없고. <code>GetInstanceID()</code> 쓰다가 런타임에 꼬여본 사람만 이 해방감을 안다.</p>
<p><strong>Read</strong>: <code>projects.filter(p =&gt; p.status === column.id)</code> 로 상태별 필터링. LINQ의 <code>.Where()</code>가 그리워질 줄 알았는데, <code>.filter()</code>도 나름 괜찮다. <code>System.Linq</code> 안 써도 되는 세상이라니.</p>
<p><strong>Update</strong>: 프로젝트 카드의 Edit 버튼 클릭 → 기존 데이터로 모달 열기 → 수정 → 저장.</p>
<p><strong>Delete</strong>: <code>window.confirm('DELETE THIS PROJECT?')</code> → 확인하면 <code>projects.filter</code>로 제거.</p>
<p><code>window.confirm</code>... 이거 웹에서도 쓰는 거구나. 유니티에서 <code>EditorUtility.DisplayDialog</code> 쓰는 것과 같다. 근데 게임 런타임에서는 못 쓰니까 직접 다이얼로그 UI 만들어야 했는데, 웹은 브라우저가 알아서 해준다. 편하다. Prefab 만들고 Canvas 위에 올리고 <code>DOTween</code>으로 페이드 애니메이션 넣고... 그 30분짜리 작업이 한 줄이라니. 이게 문명의 차이인가.</p>

<h2 id="🌪️-scene-4--localstorage-데이터가-날아가면-그건-존재하지-않았던-것">🌪️ Scene 4 : LocalStorage (데이터가 날아가면 그건 존재하지 않았던 것)</h2>
<p>Admin 대시보드에서 프로젝트를 추가하고 나서 새로고침하면... <strong>데이터가 날아갔다.</strong> <code>Destroy(gameObject)</code> 당한 느낌이었다. 아무도 호출하지 않았는데.</p>
<p>당연하다. React의 <code>useState</code>는 런타임 메모리에만 저장되니까. 유니티에서 <code>PlayerPrefs</code> 안 쓰고 그냥 변수에만 저장하면 씬 전환할 때 날아가는 것과 똑같다. <code>static</code> 변수에 넣어둬도 도메인 리로드 한 방이면 전부 <code>GC.Collect()</code> 당하는 그 허무함.</p>
<pre><code class="language-javascript">const STORAGE_KEY = 'portfolio_projects';

const loadProjects = () =&gt; {
  try {
    const stored = localStorage.getItem(STORAGE_KEY);
    return stored ? JSON.parse(stored) : DEFAULT_PROJECTS;
  } catch {
    return DEFAULT_PROJECTS;
  }
};

const saveProjects = (projects) =&gt; {
  try {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(projects));
  } catch (e) {
    console.error('Failed to save projects:', e);
  }
};</code></pre>
<p><code>localStorage.setItem</code> / <code>getItem</code>이 <code>PlayerPrefs.SetString</code> / <code>GetString</code> 같은 거다. JSON 직렬화해서 문자열로 저장하는 것도 유니티에서 데이터 저장할 때랑 똑같은 패턴. <code>JsonUtility.ToJson()</code> 해서 <code>PlayerPrefs</code>에 때려박는 그 패턴. 5년간 몸에 밴 근육 기억이 여기서 빛을 발한다.</p>
<p>그리고 <code>useEffect</code>로 <code>projects</code> 상태가 바뀔 때마다 자동 저장:</p>
<pre><code class="language-jsx">useEffect(() =&gt; {
  saveProjects(projects);
}, [projects]);</code></pre>
<p>이거 유니티에서 <code>OnApplicationPause</code>이나 <code>OnApplicationQuit</code>에서 <code>PlayerPrefs.Save()</code> 호출하는 것과 같은데, 훨씬 세밀하다. 상태가 바뀔 때마다 즉시 저장되니까. 유니티에서 이거 하려면 <code>ReactiveProperty</code> 같은 거 써야 하는데 여긴 프레임워크 레벨에서 지원해준다. 프레임워크의 복지 수준이 다르다.</p>

<h2 id="🏰-scene-5--secret-room-테마-빨간색은-항상-멋지다">🏰 Scene 5 : SECRET ROOM 테마 (빨간색은 항상 멋지다)</h2>
<p>Admin 페이지를 녹색 테마로 하면... 그냥 포트폴리오랑 똑같잖아. 비밀의 방인데 말이야. <code>Material</code>을 바꿔야 분위기가 바뀌는 법이다.</p>
<p><strong>&quot;Admin 대시보드는 빨간 계열 테마로 해줘. 비밀스러운 느낌으로.&quot;</strong></p>
<pre><code class="language-css">.admin-container {
  background: linear-gradient(180deg, #0a0505 0%, #0d0808 100%);
}

.admin-title {
  color: #ff4444;
  text-shadow: 0 0 10px rgba(255, 68, 68, 0.5);
}</code></pre>
<p>짜잔. 어두운 붉은 배경에 형광 빨간 글씨. 완전히 다른 분위기가 된다. 마치 폴아웃에서 Vault-Tec 터미널에서 Enclave 터미널로 넘어간 느낌? (Enclave가 빨간색이었나? 기억이 가물가물한데, 아무튼 비밀조직 느낌이면 된다.) URP에서 Post Processing Volume 하나 얹었더니 갑자기 호러 게임이 되는 그 느낌과 비슷하다.</p>
<p>버튼도 전부 빨간 테마. EXIT 버튼은 약간 어두운 빨간색(#aa3333)으로, 긴장감을 유발한다. &quot;여기서 나가고 싶어?&quot; 같은 느낌. <code>Application.Quit()</code> 버튼에 빨간색 넣으면 유저가 누르기 전에 한 번 더 생각하는 그 효과.</p>
<p>그리고 상태별 색상도 지정했다:</p>
<pre><code class="language-css">.status-todo { color: #ffaa00; }       /* 주황 - 아직 안 시작 */
.status-in_progress { color: #ffff44; } /* 노랑 - 진행 중 */
.status-done { color: #66ff66; }       /* 초록 - 완료 */</code></pre>
<p>선택박스(<code>&lt;select&gt;</code>)의 배경이 흰색으로 나오는 문제도 있었다. 다크모드인데 드롭다운만 눈부시게 하얗게 빛나고 있었다. 눈이 아팠다. 눈물이 날 뻔했다. <code>Bloom</code> 이펙트를 눈에 직접 쏘는 수준이었다.</p>
<pre><code class="language-css">.status-select option {
  background: #1a0808; /* 어두운 붉은 배경 */
  color: #ff6666;
}</code></pre>
<p><code>&lt;option&gt;</code> 태그는 브라우저별로 스타일 제한이 있어서 완벽하게 컨트롤하기 어렵다. 유니티의 Dropdown 컴포넌트에서 템플릿 수정하는 것처럼 자유도가 높지 않다. 브라우저가 만든 렌더링 엔진 위에서 우리가 놀고 있는 거니까 어쩔 수 없지. 이건 렌더 파이프라인을 못 바꾸는 것과 같다. Built-in RP에서 셰이더 커스텀하려다가 &quot;이건 SRP에서만 됩니다&quot; 듣는 그 좌절감과 일맥상통한다.</p>

<p>그리고 오늘 깨달은 게 있다.</p>
<p><strong>웹 개발은 결국 UI 개발이다.</strong></p>
<p>유니티에서 UI 만들 때 느꼈던 그 고통과 성취감이 그대로 여기에도 있다. 레이아웃이 안 맞아서 머리 싸매는 것도 같고, 색상 하나 바꿨는데 전체 분위기가 확 바뀌는 쾌감도 같다. 다만 React는 유니티보다 <strong>&quot;상태 관리&quot;</strong>라는 개념이 훨씬 직관적이게 느껴진다. <code>useState</code> 하나로 UI 업데이트가 끝나니까. 유니티에서 <code>OnValidate</code>, <code>OnInspectorGUI</code>, <code>UnityEvent.AddListener</code> 이리저리 꼬아야 하는 것보다 훨씬 깔끔하다. 5년간 <code>SerializedProperty</code>랑 <code>CustomEditor</code> 지옥에서 살다가 해방된 기분.</p>
<p>아, 그리고 <strong>ESLint</strong> 때문에 커밋을 3번이나 고쳤다. <code>motion.div</code>의 <code>motion</code>을 unused variable로 잡는 거 보고 10분 동안 뭐가 문제인지 몰랐다. 결국 <code>varsIgnorePattern</code> 정규식을 수정해서 해결. 웹 개발에서도 린터(Linter)는 나의 적이자 동료다. 유니티에서 컴파일 에러 잡는 것과 같은 그 러브헤이트 관계. <code>CS0219: The variable is assigned but its value is never used</code> — 이 경고 메시지가 웹에서도 나를 따라오다니. 전생에 변수를 선언만 하고 안 쓴 죄를 지었나 보다.</p>
